# Агент воркера (`dockrunner_agent`)

Ставится на каждый сервер (Ubuntu 22+), разворачивает приложения в Docker-контейнерах, слушает задачи с централи, отдаёт логи панели.

## Установка на сервер

1. Установить Docker Engine, добавить пользователя в группу `docker`.
2. Скопировать бинарь (`go build -o agent ./cmd/agent`) или собрать образ из `Dockerfile`.
3. Заполнить `.env` по `.env.example` (агент читает его из папки запуска — запускайте из корня `dockrunner_agent`, иначе тихо возьмутся дефолты и будет 403 от RabbitMQ). Главное:
   `AGENT_ID=worker-01`, `CENTRAL_URL=http://централь:8080`,
   `AGENT_TOKEN=<общий секрет>`, `RABBITMQ_URL=amqp://...` (центральная шина),
   `AGENT_DESCRIPTION=...` (описание сервера, видно в панели; пусто — не затрёт заданное админом),
   `AGENT_CITY/LAT/LNG` (место для карты — можно не задавать, тогда агент сам определит город и координаты по IP через ip-api.com; без интернета останется без метки), `AGENT_PUBLIC_URL=http://worker-01:8090` (адрес API для панели),
   `SQLITE_PATH=/data/agent.db`.

Запуск бинарём:

```bash
./agent
```

Запуск контейнером (доступ к Docker хоста + папка под SQLite):

```bash
docker build -t dockrunner-agent .
docker run -d --name agent --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /opt/agent-data:/data \
  -p 8090:8090 --env-file .env dockrunner-agent
```

## Как это работает

1. Агент коннектится к **центральной** RabbitMQ и слушает очередь `agent.<AGENT_ID>`: `prepare` (склонировать репозиторий), `deploy` (собрать и запустить), `stop`, `restart`, `remove`, `reboot`. Состояние хранит в своей SQLite, результат шлёт в очередь `events`. Задачи выполняются параллельно (до 4 одновременно, QoS prefetch=4); задачи одного проекта (`владелец/проект`) сериализуются мьютексом, `reboot` ждёт завершения всех. Poison-задачи не крутятся вечно: постоянная ошибка (нет такого деплоя, плохой том) дропается сразу с событием `op.failed`, ошибка с повторной доставки — тоже дроп, первая неудача — одна перепопытка. Исключение: `remove` идемпотентен — нет локальной записи значит удалять нечего, сразу `container.removed`, чтобы централь убрала фантомную запись.
2. Git-флоу: `prepare` клонирует репозиторий (`--depth 1`) в `WORKSPACE_DIR/<владелец>/<проект>` и проверяет корень — `Dockerfile` в любом регистре (`Dockerfile`, `dockerfile`, …) или `docker-compose.yml/.yaml`, `compose.yml/.yaml` (найденное реальное имя файла идёт дальше в сборку). Результат — событие `prepare.completed` (с найденными файлами) или `prepare.failed`. `deploy` после подтверждения обновляет код, собирает образ (`docker build` по Dockerfile либо по первому сервису compose с `build`, иначе берёт готовый `image`) и поднимает контейнер. Нужен `git` в системе (в Docker-образе уже установлен).
3. Файлы пользователя (`files.list/mkdir/upload/download` по RabbitMQ с ответом): всё строго внутри `WORKSPACE_DIR/<владелец>`, побеги через `..` и абсолютные пути наружу отклоняются.
4. Тома: `host_path` резолвится только внутри папки владельца (папка создаётся), простое имя без пути — именованный том Docker. Имя контейнера — из задачи или `app-deployment`, мусорные символы чистятся.
3. Тома: `host_path` резолвится только внутри папки владельца (`WORKSPACE_DIR/<владелец>`), наружу выйти нельзя — попытка отклоняется; простое имя без пути — именованный том Docker. Имя контейнера — из задачи или `app-deployment`, мусорные символы чистятся.
4. Кнопка «Обновить» — это повторный `deploy`/`refresh` с тем же id: агент принудительно удаляет старый одноимённый контейнер, заново качает код, пересобирает образ и стартует.
   3. Каждые 15 сек шлёт heartbeat на централь (`POST /api/v1/agents/heartbeat`): CPU/RAM/диск, число контейнеров, число потоков CPU (определяется само) и занятое место по пользователям.
   - Имя на карте: `AGENT_NAME` (по умолчанию hostname); если не задан, централь показывает hostname, затем agent_id.
   - Сеть: скорость down/up в Мбит/с между heartbeat'ами (без loopback-интерфейсов).
   - IP для портов/карты: LAN-адрес машины (с fallback на перебор интерфейсов).
3. Логи никуда не пушатся: агент держит последние 500 строк каждого контейнера в памяти. Панель забирает их сама:
   - `GET :8090/containers/{deploymentId}/logs?tail=200`
   - `GET :8090/containers/{deploymentId}/logs/stream` — WebSocket: сначала история, потом живые строки `{stream, line, time}`
   - плюс `GET /health`, `GET /containers`. Кроме `/health` нужен токен: заголовок `Bearer` или `?token=` в query (для браузера).
   - лог сборки деплоя: `GET /deployments/{id}/build-log?tail=200` (шаги Dockerfile, статусы скачивания слоёв — последние 500 строк, в SQLite, переживает рестарт), `GET /deployments/{id}/build-log/stream` — то же по WebSocket (сначала история, потом живые строки).
   - `AGENT_PUBLIC_URL` обязателен для прокси спека/логов/лога сборки через централь (без него централь отвечает «задайте AGENT_PUBLIC_URL»); при пустом агент пишет warn на старте.
4. Живая документация HTTP API — Swagger UI: `http://воркер:8090/swagger/` (генерация: `swag init -g cmd/agent/main.go -o docs`).

## Проверка

- `curl localhost:8090/health` → `{"status":"ok",...}`
- В панели сервер должен стать «готовым», деплой — появиться в событиях, логи приложения — стримиться.
- Не стартует без Docker; без RabbitMQ работает в урезанном режиме (без задач и событий), в логе будет варнинг.

## Если проверка репозитория висит

1. В панели теперь видно, от какого узла ждём ответ, сколько секунд прошло, и есть кнопка отмены.
2. Централь сразу отвечает 400, если узел не присылал heartbeat, и отдельно — если heartbeat старше 2 минут («узел не в сети»). Проверьте `AGENT_ID` воркера и что heartbeat доходит (`GET /api/v1/agents`).
3. На воркере ищите в логе `task received type=prepare`, затем `prepare started` / `prepare detected` (там же видно, что именно нашлось в корне).
4. Папка без `.git` не клонируется заново, чтобы не снести данные, — в панели придёт понятная ошибка с путём, удалите папку на воркере вручную.
5. Если проверяете одно имя приложения с разными URL — воркер сам переключит существующий клон на новый remote (`set-url` + `fetch` + `reset --hard`, нетронутые файлы не трогает). А в ошибке «не найден» теперь перечислено, что реально лежит в корне папки на воркере, — сверьте с ожидаемым.
